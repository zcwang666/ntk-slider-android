## 1. 设备与传输层

| 项目 | 值 |
|---|---|
| 设备名（用于扫描过滤） | `NTK-1`、`NTK-1 AT+NAMENTK-1`、`JDY-19` |
| 蓝牙模组 | JDY-19（透传型 BLE 模块，从名称判断） |
| Service UUID | **未硬编码**，取第一个 `isPrimary` 的服务 |
| 写特征 | 该服务下第一个 `properties.write` 的特征 |
| 通知特征 | 该服务下第一个 `properties.notify / indicate` 的特征 |
| 写入方式 | `wx.writeBLECharacteristicValue`（带响应写） |
| 分包 | 无：所有指令均为 6 字节，一次写入 |

**这意味着新 App 无需事先知道 UUID**，沿用"自动发现第一个可写/可通知特征"的策略即可；但要加一层白名单校验（见 §6 风险）。

## 2. 帧格式

### 2.1 下行（App → 设备）

```
A5 5A | 04 | CMD_H | CMD_L | AA
 帧头    长度   命令字(2字节)  帧尾
```

- 长度字段 `04`：自长度字节起算到帧尾的字节数（`04 + CMD_H + CMD_L + AA` = 4）。
- 全部 78 条指令均为该结构，**没有可变数据段**，不存在动态拼包。

### 2.2 上行（设备 → App）

官方解析逻辑的偏移量反推出结构：

```
A5 5A | LEN | CMD | DATA_H | DATA_L | X | AA
                 └─ 有效数据 16 位大端 ─┘
```

- App 读取 `CMD`（第 4 字节）判类型，读 `DATA_H/DATA_L`（第 5–6 字节）为 **16 位大端数值**。
- 第 7 字节官方**从未读取**，其是否为校验和无法从代码确认（见 §2.3）。

### 2.3 待确认项：第 7 字节

- 存在反例：`A55A04E7B6AA` 与 `A55A04E7B9AA` 仅末字节不同却语义不同，说明**末字节不是命令字的校验和**；
- 因此本方案将其视为**命令字的一部分**（即 2 字节命令），并要求用以下任一方式在真机上确认：
  1. 用 nRF Connect / LightBlue 直接在真机上抓一次官方小程序的下行帧；
  2. 或对设备做 `A55A04` + `XXYY` + `AA` 的穷举试探（分帧发送，观察是否有回应/动作）。

> **对复刻的影响：无。** 我们逐字节复刻官方下行帧即可 100% 行为一致；只有"新增指令"才需要固件方提供文档。

## 6. 原版实现缺陷清单（重写时逐条修复）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | `that` 变量从未定义却直接使用 | `onShow`、`lock`、`setup_0` | 每次进入首页即抛 `ReferenceError`，出厂提示永不显示 |
| 2 | `deviceId` 未保存到 `data`，断开时传 `undefined` | `closeBLEConnection` | 无法定向断开，只能靠重启适配器 |
| 3 | 特征发现循环内重复发送握手帧 | `getBLEDeviceCharacteristics` | 每个特征都写一次，指令风暴 |
| 4 | `onBLECharacteristicValueChange` 在特征发现里注册 | 同上 | 重复连接会叠加多个监听器，状态错乱 |
| 5 | 接收缓冲用字符串前缀匹配，未找到完整帧也不回滚 | 通知回调 | 帧被截断时错位解析；`user_str` 无上限增长（内存泄漏） |
| 6 | 每 1 秒轮询、5 秒强制重启蓝牙适配器 | `sinx` 定时器 | 无谓功耗；重连瞬间丢指令 |
| 7 | 无写入队列与超时重发 | 全局 | 连续点按时 BLE 栈丢包，表现为"按键无反应" |
| 8 | 无连接状态机 | 全局 | 断连后界面仍显示旧状态 |

## 7. 复刻实现建议

1. **协议层与 UI 层彻底解耦**：`frame codec（字节层）→ command catalog（78 条语义）→ state store（30 类上报）→ UI`。
2. **保留"字节级兼容"**：先做到 1:1 复刻，保证替换 App 后设备行为不变。
3. **接收改为二进制缓冲**：`ByteArray` + 环形缓冲，按 `A5 5A` 定位、按长度字段切帧，解析失败回退而不是丢弃。
4. **写入串行化**：单条指令队列 + 20 ms 间隔 + 失败重试 2 次。
5. **状态以设备上报为准**：App 只做乐观更新，收到上报后覆盖。
